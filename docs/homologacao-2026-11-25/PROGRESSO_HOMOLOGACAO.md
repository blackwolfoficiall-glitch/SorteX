## Como repetir o teste local

1. Crie um PostgreSQL descartável e aplique as migrações com `prisma migrate deploy`. Não reutilize a URL de uma base de homologação compartilhada ou produção.
2. Rode a API Nest de desenvolvimento em `127.0.0.1:3338` com chaves locais novas, `PAYMENT_ENV=test`, sem credenciais dos provedores e com `APP_VERSION` igual ao SHA validado. Configure o Next com `API_INTERNAL_URL` e `SORTEX_HOMOLOGATION_API_URL` iguais ao endereço local dessa API.
3. Em `apps/mobile`, execute `SORTEX_PARITY_WEB=http://127.0.0.1:4408 SORTEX_PARITY_API=http://127.0.0.1:3338 node --import tsx scripts/test-web-ios-parity.ts`. O teste rejeita URL remota/API não marcada como desenvolvimento e escreve apenas dados sintéticos. Ele não publica campanhas nem toca pagamentos.
4. Em `apps/web`, execute `node --test lib/api-upstream.test.mjs` com Node 22+ que suporte TypeScript nativo, ou use a versão Node 24 da validação.

## Renovação de sessão

A API agora vincula cada renovação à credencial completa e emite um identificador novo por refresh, inclusive para renovações no mesmo segundo. A alteração não apaga contas nem modifica a tabela de sessões. Registros de refresh legados deixam de renovar; na implantação aprovada, comunique que esses usuários precisam reautenticar. Esse comportamento foi testado no backend, não no SecureStore do aparelho.

### Bootstrap preparado para a mesma API

A candidata iOS agora usa por padrão a URL reservada ao slug `sortexqa` no projeto isolado. O iniciador só considera a candidata pronta se `/health/ready` confirmar o schema; a Fase 1 continua separada. Na Netlify foi criado o projeto vazio **sortex-web-ios-qa**, separado e restrito ao login da equipe. Ainda não houve build do site nesse projeto. As três tentativas de gravar as variáveis pelo conector receberam HTTP 403; não afetam os sites anteriores.

Para o bootstrap no GitHub, configurar em Settings → Environments o ambiente `sortex-web-ios-qa` restrito exclusivamente à branch `homologacao/web-ios-integrada` (sem tags ou pull requests). Definir a variável de ambiente `SORTEX_QA_BOOTSTRAP=yes` e os **secrets do ambiente**, não do repositório: `SORTEX_QA_DATABASE_URL` (conexão direta com TLS do banco vazio `neondb`) e `SORTEX_QA_NEON_API_KEY` (chave de escopo exclusivo ao projeto QA). Nunca enviar os valores por chat ou commit. Depois reexecutar o workflow **Bootstrap isolado SorteX Web + iOS** iniciado pelo push. Ele verifica o destino, aplica apenas as migrações versionadas, empacota a API e verifica prontidão e SHA. Se o Neon já tiver uma função nesse projeto, o bootstrap recusa sobrescrevê-la.

No projeto **novo** da Netlify, vincular somente a branch de integração e definir `SORTEX_HOMOLOGATION_API_URL`, `API_INTERNAL_URL` e `API_URL` para a URL HTTPS confirmada da nova API, em Builds e Functions. Manter acesso restrito, revisar o primeiro deploy e confrontar a revisão direta da API com a exposta pelo BFF do novo site. Não redirecionar os ambientes anteriores. O aceite da implantação exige repetir cadastro/login e conferir o mesmo ID nos dois clientes; o aceite iOS físico vem depois.
