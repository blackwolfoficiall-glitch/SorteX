# Compatibilidade da janela de vendas do comprador

O checkout usa o estado `salesWindow` quando a API o fornece. A API anterior de homologação (revisão `48eeb858`) não o fornece. Nesse caso, o cliente só aplica as comparações da API anterior se a resposta real da campanha publicada trouxer os três campos absolutos em UTC (`salesStartAt`, `salesEndAt` e `drawDate`, inclusive valores nulos explícitos) e não indicar bloqueio de compra. O horário civil do sorteio não substitui a data absoluta legada. Um retorno incompleto ou incompatível oculta novas operações e mostra uma mensagem de indisponibilidade; a API continua sendo a autoridade final.

No iOS, a disponibilidade legada só é complementada pelo detalhe ao vivo se o ID e o slug coincidirem. A consulta da reserva existente não passa pela nova janela, e a retomada da mesma chave continua disponível. Na web, o painel de compra, o botão fixo e os combos ficam indisponíveis para novas operações fora da janela. Nem o preview do organizador nem o checkout de um pedido já criado são alterados.

## Evidência local

- Web anterior, da mesma árvore Web publicada em `09a0f9a`, com Nest `48eeb858`: reserva incorretamente habilitada nas campanhas com vendas futuras, encerradas e sorteio passado. Reprodução em Chromium e WebKit com perfil iPhone 13.
- Web corrigida + API legada e Web corrigida + API candidata: duas provas de navegador por combinação, atravessando o BFF Next e Nest reais. Futuro mostrou “As vendas ainda não começaram.” e bloqueou reserva; encerrada e sorteio passado também bloquearam; campanha aberta manteve a disponibilidade. Na candidata, detalhe e disponibilidade retornaram o mesmo estado.
- O cliente HTTP do app, autenticado com duas contas sintéticas independentes, conferiu os mesmos quatro estados em ambas as APIs, suas rejeições reais para novas reservas fechadas, abertura permitida e retomada idempotente da reserva ativa, inclusive após fechar a mesma campanha. O PostgreSQL descartável recebeu as 21 migrações legadas antes de semear os registros e depois a 22ª; nenhum provedor chamado, nenhuma linha de pagamento.
- A execução usa binário Nest legado na revisão exata e binário Nest candidato com a mesma árvore de runtime e schema de `5940262`. TypeScript móvel, 98 testes móveis e build de produção Next passaram. WebKit não equivale a teste no aplicativo iOS ou no aparelho.

Para repetir, use apenas um PostgreSQL descartável em loopback, sem integrações de pagamento, com um organizador fictício aprovado e quatro campanhas publicadas `synthetic-window-{future,ended,drawn,open}`. Fixe início, fim e sorteio em lados opostos do instante de teste conforme cada nome. Com Next apontando explicitamente para a API local, use `SORTEX_SALES_WINDOW_PAIR=legacy|matched PLAYWRIGHT_BASE_URL=http://127.0.0.1:<porta> npx playwright test --config playwright.buyer-sales-window.config.ts` (use o modo `legacy-baseline` apenas para reproduzir a falha na versão Web anterior). O script `apps/mobile/scripts/test-buyer-sales-window-local.ts` recusa servidores não locais e exige conta `@example.test`; o modo `SORTEX_SALES_WINDOW_POST_CLOSE=1` é para repetir o pedido depois de encerrar a mesma campanha no banco descartável. Nenhum ambiente compartilhado foi modificado.
